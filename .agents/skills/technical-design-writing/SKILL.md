# 技术方案写作

编写让目标读者在阅读代码前就能理解设计的中文技术方案。先建立问题、约束、运行过程和决策依据，再介绍技术抽象与实现计划。

除非用户明确指定其他读者，默认读者只具备刚入职校招生的技术水平。他们了解基础软件概念，但不了解本项目、NSW 电力市场、储能业务、研究协议和现有实现。文档必须从业务背景和项目语境讲起，不能依赖这些前置知识。

通俗易懂是首要表达目标。保留准确性所需的术语和条件，但不要用术语数量体现专业性。读者应能用自己的话说清“它是什么、为什么需要、具体怎样运行、哪些情况下不成立”。

## 权威边界

开始写作前：

1. 阅读仓库根目录的 `AGENTS.md`，将其视为项目约定的主要来源；本 Skill 不改变上层指令或用户明确要求的优先关系。
2. 按主题读取 `docs/` 下相关的当前有效文档和代码。历史计划的访问与引用遵循 `AGENTS.md`：仅在用户明确要求参考时读取 `docs/old_plan/`，并标明其历史性质，不将其作为当前契约。
3. 服从用户对文档目标、读者、范围和格式的明确要求。用户要求与默认结构不同时，保留用户选择。
4. 区分事实、推断、假设和建议。可变化的市场事实优先核验 AEMO、AEMC 或 AER 一手资料，并标注核验日期。
5. 若用户只要求方案或评审，不得据此修改实现代码。

创建完整方案、系统性重写方案或执行正式方案评审时，阅读全文 [技术方案写作详细规范](references/writing-standard.md)。仅回答一个局部写作问题时，可直接使用本入口中的原则。

## 写作流程

### 1. 明确文档任务

先确定：

- 文档要支持什么决策；
- 默认按“刚入职校招生的技术水平，且不了解本项目和业务背景”组织解释；用户另有指定时再调整；
- 本次解决与明确不解决的范围；
- 输出是新方案、现有方案重写，还是基于证据的评审。

不要在缺少关键字段、时间语义、价格版本、资产约束或费用定义时生成确定性结论。无法从仓库和一手资料确认的内容应标记为待定义参数或未验证假设。

### 2. 先建立问题和现状

用具体业务或研究场景说明：

- 当前系统或研究链路如何运行；
- 当前问题在什么情况下出现；
- 问题造成什么实际影响；
- 为什么现在需要调整。

不得从类名、接口、Schema、文件树或模块清单起笔。

### 3. 按因果顺序提出设计

技术抽象按以下顺序引入：

`现实问题 → 设计需求 → 抽象概念 → 技术命名`

每个关键设计决策至少说明：问题、方案、选择原因和预期结果。存在有现实意义的替代方案时，说明未选择的原因；不要为显得完整而罗列无关选项。

### 4. 让读者看到系统如何运行

涉及流程、算法、数据处理、Agent、任务调度、接口调用或滚动决策时，提供至少一个具体、按时间顺序展开的运行案例。先展示端到端数据流，再映射到模块和代码。

对狭窄的局部决策，可使用更小的场景例子，不必机械扩写成完整系统案例。

复杂流程先用几句话讲清主线，再沿同一个例子逐步展开。每一步说明：已知什么、做了什么、得到什么、结果交给谁；涉及判断或循环时，补充判断依据、下一步和状态如何变化。先走通正常流程，再在相关位置解释重要异常，避免把所有分支塞进一个长句。

当时间先后、分支、反馈循环或多方交互是理解难点时，默认配图；简单关系用文字或表格即可。先明确图要回答的问题，再选时间线、流程图、时序图或状态图。简单流程优先使用 Mermaid；需要精确对齐的时间线、路径重排、并列结构和能量／计量边界时，优先考虑可维护的 SVG；一张图只解释一个主要问题，节点用已解释的中文概念和具体动作，箭头说清关系。图前说明看什么，图后解释关键结论。不设固定图数，也不要求把现有 Mermaid 全部转成 SVG。新增、修改或迁移配图时，读取详细规范第 7 节。

重写前盘点原文图片与 Mermaid，逐一判断保留、修改、替换或删除，不能因章节重组遗漏有效图示。图与正文一起维护，沿用已解释的案例与术语，说明单位、箭头及教学简化；修改共享图前检查其他引用，交付前核对路径、图号并实际渲染检查。

### 5. 再展开技术细节

介绍业务、市场、模块、数据模型、公式、算法和接口时：

- 对理解设计所必需、且目标读者不熟悉的概念，首次使用时先用日常语言解释它是什么、解决什么问题；关键难点再给一个有具体时间、数值或对象的小例子，并指出容易误解的边界。不能用另一个未解释的术语解释它。基础软件概念无需重新定义；本项目赋予其不同含义时，解释该差异；
- 英文名称或缩写不直观时，再补充名称含义；不得用名称解释代替上述概念说明；
- 模块说明职责、不负责的内容、输入、输出、独立存在的原因和上下游关系；
- 变量说明含义、单位、正负方向和数据来源；
- Schema 之前先说明生产者、消费者和字段存在的原因；
- 算法按“思想 → 示例 → 必要时的伪代码”展开；
- 公式先说明它在计算什么，再定义符号并展示公式；关键换算或难懂公式给出带单位的代入示例，解释结果意味着什么。示例中的假设和简化必须明说，不得冒充实验结果；
- 大段 Schema、接口、SQL、配置和伪代码放到实现细节或附录。

正文只引入当前理解所需的概念。主线中一旦连续依赖多个新概念，先拆开解释再继续；完整定义、推导和实现细节放到后面。类比可用于建立直觉，但要说明它不能代表的技术性质，不能替代准确解释。

### 6. 最后给出落地路径

主设计讲清楚后，再说明：

- 对现有数据、模块、接口和实验的影响；
- 分阶段实施步骤及涉及文件；
- 测试与验收标准；
- 迁移、回滚、降级或停止条件；
- 未验证内容、已知风险和结论边界。

实施计划不能代替设计说明，文件和代码修改清单不得成为正文主体。

## 本项目方案的必要契约

当方案触及数据、预测、概率校准、滚动优化、储能回测或经济核算时，显式覆盖相关项目契约：

- 目标区域是 NSW1，标签和结算价格不得与其他区域混用；
- 第一阶段每 5 分钟决策一次，预测未来 60 分钟，`h = 1...12`；核心领域结构不得把 12 步写死；
- 市场时间使用 AEST（UTC+10）和 interval-ending 语义；区分 nominal run time、available time、issue time、target interval end、ingestion time 与价格修订时间；
- 说明 P5MIN forecast vintage 的选择规则，且所有输入在决策时点真实可见；
- 说明 NSW1 RRP 的字段、价格版本、单位、来源和数据区间；
- 概率预测至少输出 P10、P50、P90，并交代校准、事件概率、基线和滚动切分；
- 说明储能、站点、费用、退化、风险、期末 SOC 和结算假设，不得把缺失费用静默设为零；
- 方案说明预测、事件与运营评价的方法、与原始 P5MIN 或预注册基线的比较方式及验收条件；已有实验结果时引用证据，尚未执行时明确标记。仅因编写或评审方案，不新增训练或回测任务；
- 将离线研究、合成资产和参数化费用的结果明确限定为假设下的历史回测，不表述为真实商业收益或部署承诺。

根据主题读取 `docs/DATA_CONTRACT.md`、`docs/FORECAST_PROTOCOL.md`、`docs/BESS_BACKTEST_PROTOCOL.md`、`docs/RESEARCH_SCOPE.md` 或 `docs/EXPERIMENT_TEMPLATE.md`，不要把这些契约全文复制进方案。

## 默认组织方式

根据主题裁剪章节，不要求机械保留所有标题。通常按以下顺序组织：

1. 执行摘要或结论；
2. 背景与当前问题；
3. 设计目标和非目标；
4. 核心设计思路与关键决策；
5. 一个完整运行示例；
6. 整体流程与数据流；
7. 模块、数据模型和关键算法；
8. 异常、边界场景与降级；
9. 技术选型与取舍；
10. 对现有系统的影响；
11. 实施步骤、测试和验收；
12. 风险、未决项与附录。

简单方案应保持简短；复杂方案可以扩展，但不能让细节掩盖主线。局部修订只补足相关上下文，不强制重写整篇文档。

## 交付前检查

从读者视角检查：

- 一名不了解本项目和业务背景、只有刚入职校招生技术水平的读者，是否能理解问题背景和完整流程；
- 是否先解释为什么，再解释怎么做；
- 是否有未解释的业务概念、英文名、缩写、变量或内部术语；
- 理解设计所必需、且目标读者不熟悉的项目概念，是否在首次使用处解释含义与作用，并在影响理解时展开上下游关系；
- 是否能在不阅读代码的情况下复述系统运行过程；
- 能否跟随例子说出每一步的输入、动作、结果，以及重要分支为何发生；
- 难点是否有真正帮助理解的例子或图，图中的时间、单位、箭头与正文是否一致；
- 重写是否遗漏有效旧图，共享图片的其他引用处、图号和相对路径是否仍然正确；
- 新增或修改的图是否通过语法和实际渲染检查，未完成的视觉验证是否明确说明；
- 是否把分位数、预测区间或其他带条件的结论，简化成了确定保证；
- 是否出现名词堆砌、无原因的技术选型或过早的代码细节；
- 是否明确区分事实、推断、假设和建议；
- 是否遗漏信息可见性、单位、费用、物理约束、比较基线或结论边界；
- 是否与 `AGENTS.md` 及当前有效协议一致；
- 是否把实现计划放在设计说明之后。

最重要的判断标准：不要要求读者先理解代码，才能理解设计。
